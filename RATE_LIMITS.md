# Общие MongoDB-лимиты аккаунтов

## Контракт

| Действие | Scope | Лимит на IP | Окно |
|---|---|---|---|
| Регистрация | signup | 5 | 60 минут |
| Вход | signin | 15 | 15 минут |
| Запрос письма восстановления | forgot-password | 5 | 15 минут |
| Установка нового пароля | reset-password | 10 | 15 минут |

Подсчитываются все попытки, включая невалидные данные и неизвестные email.
Прежние адреса API, пороги и разделение действий сохранены. Окно начинается
с первой попытки; отклонённые запросы не продлевают его. Ошибка превышения:

```json
{
  "code": "RATE_LIMITED",
  "message": "Too many attempts. Please try again later.",
  "retryAfter": 900
}
```

HTTP 429, заголовок Retry-After содержит тот же целочисленный остаток в секундах,
округлённый вверх, минимум 1. Прежний message сохранён для старых клиентов.
Код REQUEST_LIMITED остаётся в контракте, но прежний аварийный предел 10000
записей локального Map удалён вместе с Map: это была защита памяти процесса,
не пользовательская квота. Не появился общий глобальный лимит в 10000 IP.

При недоступной базе/истечении срока операции/неверном результате — HTTP 503,
code RATE_LIMIT_UNAVAILABLE, Cache-Control: no-store. Обработчик аккаунта НЕ
выполняется. Retry-After не выдумывается, поскольку окно достоверно неизвестно.
Сообщение переведено на en/de/qt/ru; qt требует обычной вычитки носителем.
Сырые ошибки драйвера, URI, реквизиты и содержимое запросов не логируются.
Нельзя переключаться на локальный счётчик или пропускать запрос при отказе БД.

## Атомарность и время

Коллекция auth_rate_limits находится в той же базе подключения URI/dbName,
что приложение. Никакие реальные подключения в этом этапе не выполнялись.
Все экземпляры backend должны использовать одну базу и одинаковые пороги/scopes.

Один документ на scope + SHA-256 нормализованного IP; _id уникален по встроенному
индексу MongoDB. IPv4 и ::ffff:IPv4 делят квоту. В коллекцию не пишется открытый IP;
это псевдонимизация, не гарантия анонимности. Клиентский X-Forwarded-For напрямую
не используется: остаются req.ip и прежняя настройка доверенного прокси.

Одна findOneAndUpdate с aggregation pipeline атомарно:

1. Сравнивает until с MongoDB $$NOW.
2. Если окна нет/оно истекло — устанавливает count=1 и until=NOW+windowMs.
3. Иначе увеличивает счётчик, максимум до limit+1, сохраняя исходный until.
4. Возвращает документ после изменения; остаток считается по серверному
   observedAt, без зависимости от часов отдельного Node-процесса.

Никакой последовательности read → modify → save и локального кэша квот нет.
При конфликте первоначальной вставки E11000 — один повтор по тому же _id.
При неоднозначном таймауте подтверждения запрос блокируется; счётчик мог уже
увеличиться и не компенсируется. Это консервативное поведение без обхода лимита.
Write concern majority; timeoutMS драйвера 3000 мс на одну операцию, включая
ожидание соединения/подтверждения. Повтор E11000 может занять ещё одну операцию.
Buffering Mongoose для этой коллекции отключён. Новых зависимостей нет.

## TTL и требования к базе

TTL-индекс { until: 1 }, expireAfterSeconds: 0 удаляет только истёкшие документы.
Он объявлен в модели; при обычном autoIndex Mongoose создаст его при подключении.
Если autoIndex выключен, создать этот индекс отдельно в ТЕСТОВОЙ базе через
управляемое изменение инфраструктуры. Нужны права записи/создания коллекции
и индекса в соответствующей базе. Не очищать коллекцию целиком по расписанию:
удаление активных документов сбросит квоты.

TTL — экономия места, а не часть решения «разрешить/запретить». MongoDB может
удалять записи с задержкой: pipeline сам начинает новое окно по until.
Работа корректна и без очистки, и после удаления действительно истёкшей записи.

Требуются MongoDB с update pipelines/$$NOW (4.2+) и установленный в проекте
Node MongoDB driver с поддержкой timeoutMS. Для размещения использовать актуальный
поддерживаемый Atlas. Сам limiter не требует replica set; checkout по-прежнему
требует транзакций. Поддержку старой версии сервера/нештатного хранилища не
проверяли; неподдерживаемая операция вернёт безопасный 503.

При первом переходе с Map активные старые счётчики автоматически перенести
невозможно: однажды начнутся новые окна. Для staging переключить все экземпляры
на новую версию; не оставлять старый backend с Map параллельно как способ обхода.
Последующие перезапуски и увеличение числа процессов квоты не сбрасывают.
Смена имени scope/префикса _id — изменение квот, не косметическое переименование.

## Проверки и предел доказательств

- 80 параллельных вызовов через два разных экземпляра middleware: разрешены 5.
- Два отдельных HTTP Express-сервера с одной подменённой коллекцией: общая квота,
  тот же 429/code/message/Retry-After.
- Новый экземпляр middleware имитирует перезапуск и видит исчерпанную квоту.
- Граница окна, округление секунд, задержанный TTL и очистка перед новой попыткой.
- Разные scopes/IP, IPv4-mapped адрес, E11000, отказ/возврат БД, пустой результат
  и неоднозначный таймаут уже записанной попытки.
- Прежние HTTP-тесты регистрации, входа, восстановления и proxy-IP используют
  реальное middleware с подменой только метода коллекции.

Подмена выполняет pipeline-выражения и имитирует атомарную операцию; она не
доказывает сетевые свойства MongoDB, работу primary/failover или реальные процессы
на разных машинах. Реальная БД не подключалась. Добавлена отдельная opt-in
интеграционная проверка backend/tests/authRateLimit.integration.test.js.

Для неё задать RATE_LIMIT_TEST_URI в окружении тестового процесса/секретах CI,
строго с базой kitapstore_rate_limit_test, затем выполнить:

```sh
node --test backend/tests/authRateLimit.integration.test.js
```

Тест НЕ загружает backend/.env и НЕ использует URI приложения. Создаёт собственную
случайно названную коллекцию только в указанной тестовой базе, проверяет реальные
параллельные операции/сброс истёкшего окна и удаляет только свою коллекцию.
Не вставлять URI в чат, команду с сохранением истории или Git. Без этой переменной
тест пропускается; нельзя называть его пройденным. В этом этапе он пропущен.

Перед публикацией проверить TTL-индекс, права БД и этот тест на отдельном Atlas,
затем повторить 429 и отказ доступа БД в изолированном staging. Настройка trust
proxy по STAGING_DEPLOYMENT.md остаётся обязательной: общая база не исправляет
неверно определённый клиентский IP. Новых runtime-переменных нет, .env не менялся.
