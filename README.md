# Kitapstore

Книжный магазин: React + Vite (`frontend`), Express + Mongoose (`backend`).
Реализованы основа запуска, регистрация, вход и управление сессиями.
Восстановление пароля реализовано; настройка описана ниже.

## Требования и установка

Используйте Node.js 22.12+ либо актуальную LTS 24 и npm. Проверено на Node 24.15.
Нужна запущенная MongoDB локально либо доступный кластер Atlas.

```bash
cd backend
npm ci
cp .env.example .env
cd ../frontend
npm ci
cp .env.example .env
```

Если `.env` уже существует, не перезаписывайте его: добавьте недостающие настройки
вручную. Реальные `.env` исключены из Git; `.env.example` можно коммитить.

## Настройки backend

Файл `backend/.env` загружается независимо от текущей папки запуска.

| Переменная | Назначение |
| --- | --- |
| `URI` | Обязательная строка MongoDB, например `mongodb://127.0.0.1:27017/kitapstore` |
| `JWT_SECRET` | Обязательный случайный секрет для подписи и проверки JWT |
| `PORT` | Порт API, по умолчанию `1001` |
| `FRONTEND_URL` | Точный origin frontend для CORS и OAuth, по умолчанию `http://localhost:5173` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Необязательные настройки Google OAuth; без них обычный вход работает |
| `GOOGLE_CALLBACK_URL` | Callback Google, по умолчанию `http://localhost:1001/api/v1/user/auth/google/callback` |
| `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_USER`, `EMAIL_PASS` | Необязательный SMTP; порт `465` использует TLS, `587` — STARTTLS |
| `EMAIL_TO` | Получатель сообщений формы контактов и уведомлений о регистрации |

Секрет можно сгенерировать командой `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
и сохранить только в локальном окружении.

Для Atlas создайте пользователя базы, разрешите IP backend и скопируйте строку
из Connect → Drivers. Укажите имя базы `kitapstore` перед `?`, подставьте пароль
с URL-кодированием специальных символов. URI никогда не помещается во frontend.

При отсутствии `URI`/`JWT_SECRET`, некорректном порте или недоступной базе backend
завершается с кодом 1. HTTP-порт открывается только после подключения MongoDB.
Ошибка подключения не выводит URI и пароль.

## Настройки frontend

В `frontend/.env`: `VITE_API_URL=http://localhost:1001` — origin backend без `/api/v1`.
Все запросы используют `frontend/src/config/api.js`. Для reverse proxy с `/api`
на том же домене можно указать `VITE_API_URL=`. Перезапускайте Vite после изменения;
production-сборку нужно собрать заново. Переменные `VITE_*` публичны: секретов в них быть не должно.

## Запуск

В двух терминалах из корня проекта:

```bash
npm run dev --prefix backend
```

```bash
npm run dev --prefix frontend -- --host 127.0.0.1 --port 5173 --strictPort
```

Откройте `http://localhost:5173`. Проверка API: `http://localhost:1001/api/v1/test`
должна вернуть `API OK`. Если порт frontend изменён, согласуйте `FRONTEND_URL`.

## Совместимость и OAuth

Сохранены `/api/v1/<операция>` для книг и старых запросов корзины, избранного
и заказов. Также работают `/api/v1/books`, `/api/v1/cart`, `/api/v1/favourites`,
`/api/v1/orders` с прежними именами операций.

Google: начало входа `/api/v1/user/auth/google`, callback
`/api/v1/user/auth/google/callback`. Настройте в Google точный callback URL.
Без стратегии endpoint возвращает 503, а сервер продолжает работать.
Facebook пока не реализован: существующие endpoints отвечают 503 вместо ошибки Passport.
Аккаунты с существующим email автоматически не связываются с Google.

JWT выдаётся и проверяется единым модулем, срок — 7 дней. Старые токены без `id`
потребуют повторного входа. Заголовок `id` поддержан для совместимости, но должен
совпадать с подписанным идентификатором; при его отсутствии ID берётся из JWT.
Смена `JWT_SECRET` делает выданные токены недействительными.

Регистрация не зависит от SMTP. Если почта не настроена, уведомления пропускаются;
ошибка отправки не отменяет уже сохранённый аккаунт. Форма контактов требует SMTP.

```bash

npm run build --prefix frontend

```

Backend-тесты используют фиктивные настройки и подменяют обращения к базе:

Для проверки реальной настройки запустите backend: сначала должно появиться
`Connected to Database`, затем `Server running on port ...`. После этого проверьте

## Аккаунты: регистрация, вход и сессии

Регистрация принимает `username`, `email`, `password`, `address`. Имя обрезается
по краям и содержит 4–50 букв/цифр, пробелов, точек, дефисов или подчёркиваний.
Email обрезается и приводится к нижнему регистру; адрес обязателен, до 500 символов.
Новый пароль содержит минимум 8 символов и максимум 72 UTF-8 байта — это предел
bcrypt, который нельзя молча превышать. Хеширование: bcrypt с cost 12.
Поля `role`, `authProvider`, `sessionVersion` из запроса регистрации игнорируются.
Дубли имени/email дают 409, включая конфликт уникального индекса при параллельной
регистрации. Существующие email в другом регистре находятся без миграции данных.
Уникальные индексы `username` и `email` из схемы должны присутствовать в MongoDB.

Вход `/api/v1/user/sign-in` принимает прежнее поле `username`: в нём допустимы
имя пользователя или email. Неверные реквизиты дают одинаковый ответ 401;
ошибки полей — 400 с объектом `errors`, временная недоступность — 503.
Регистрация теперь возвращает 201. Текущий пользователь возвращается через
`GET /api/v1/user/get-user-information`, без хеша и служебных полей сессии.

Сохранён Bearer JWT, поскольку существующие страницы уже используют этот механизм.
Токен действует 7 дней и хранится в localStorage; это сохраняет совместимость,
но делает защиту от XSS обязательной. Сервер на каждом приватном запросе проверяет
подпись, срок, наличие пользователя и `sessionVersion` в MongoDB. Роль всегда
берётся из базы, а не из присланного токена или localStorage.

`POST /api/v1/user/sign-out` увеличивает `sessionVersion`, поэтому **выход завершает
все сессии аккаунта на всех устройствах**. Если поле отсутствует у старого аккаунта,
оно считается равным 0. Данные пользователей не мигрируются и не удаляются.
При недоступности сервера выход показывает ошибку и позволяет повторить попытку;
он не сообщает об успешном отзыве токена. Для сохранения версии при существующем
Google-входе добавлена только выборка служебного поля; провайдерный сценарий не развивается.

Frontend централизованно добавляет Authorization только к своему API, восстанавливает
сессию через сервер после обновления страницы, обрабатывает истечение токена и 401,
синхронизирует вход/выход между вкладками. При сетевом сбое восстановления сессии токен сохраняется,
но приватные страницы закрываются до успешной повторной проверки. Удаляются только
ключи `token`, `id`, `role`; остальные настройки localStorage сохраняются.
Гости перенаправляются на login с возвратом на исходную приватную страницу после входа.
Защищены профиль, корзина и существующие страницы управления; административные API
дополнительно проверяют роль на сервере. Новых возможностей админки нет.

Ограничения частоты: 5 попыток регистрации за час и 15 попыток входа за 15 минут
с одного IP, включая неуспешные. Ответ 429 содержит `Retry-After`. Счётчики хранятся
в памяти одного процесса и сбрасываются при перезапуске. Для нескольких экземпляров
нужно общее хранилище лимитов; за reverse proxy следует отдельно настроить доверие
только к известным прокси. Произвольный X-Forwarded-For не используется.

Дополнительные проверки frontend: `npm test --prefix frontend`. Они используют
реальные interceptors Axios с тестовым adapter и проверяют восстановление, выход,
истечение, сетевые ошибки, вкладки и запоздавшие ответы. Backend-тесты проверяют
HTTP-сценарии с моделью MongoDB, подменённой на данные в памяти; рабочая база
и SMTP не используются. Браузерный сценарий можно проверять отдельно с тестовой базой.

Отдельно дорабатываются подтверждение email, удаление аккаунта и бизнес-логика заказов.

Рекомендуемые коммиты этого этапа: [ACCOUNT_COMMITS.md](ACCOUNT_COMMITS.md).


Дополнение проверки аккаунтов: защита от запоздавших ответов входа/выхода
покрыта отдельным frontend-тестом. История заказов использует общую обработку
сессии и не очищает её при ответе 403. Итоговые проверки этого прохода:
9 backend-тестов, 3 frontend-теста, успешная сборка, 0 ошибок линтера
и 9 предупреждений useEffect. Год в подвале обновлён на 2026.

## Восстановление пароля: текущая реализация

Этот раздел заменяет прежние заметки о незавершённом восстановлении.
На странице входа есть ссылка «Забыли пароль?». `/forgot-password` принимает
email, `/reset-password` — новый пароль и подтверждение. Формы поддерживают
мобильный экран, Enter, ошибки полей и блокировку повторной отправки.
Пароль: минимум 8 символов, максимум 72 байта UTF-8, как при регистрации.

### Настройка почты вручную

Дополните **backend/.env** значениями своего SMTP-провайдера по
**backend/.env.example**. Реальные секреты не коммитить:

```dotenv
FRONTEND_URL=http://localhost:5173
EMAIL_HOST=smtp.example.com
EMAIL_PORT=587
EMAIL_USER=your-smtp-user
EMAIL_PASS=your-smtp-password
EMAIL_FROM=KitapStore <verified-sender@example.com>
PASSWORD_RESET_TTL_MINUTES=30
```

Это шаблон, а не рабочие учётные данные. EMAIL_FROM необязателен и по умолчанию
равен EMAIL_USER. Провайдер должен разрешать отправку от указанного адреса;
могут понадобиться пароль приложения, подтверждение домена, SPF/DKIM.
EMAIL_TO используется формой контактов, но не восстановлением: письмо уходит
на email аккаунта. Для 465 используется TLS сразу, для 587 — обязательный STARTTLS.
Самоподписанные сертификаты и открытый SMTP без TLS не поддерживаются.

В production установите FRONTEND_URL в настоящий HTTPS-origin магазина без пути,
запроса и фрагмента. Настройка также используется для CORS/OAuth.
После изменения .env перезапустите backend. Настройте SPA fallback на index.html,
чтобы /reset-password открывался напрямую из почты. Срок ссылки задаёт
PASSWORD_RESET_TTL_MINUTES: 1–120 минут, по умолчанию 30.

### API и поведение

- POST /api/v1/user/forgot-password, тело с полем email. Для существующего,
  неизвестного и OAuth-only аккаунта — одинаковый 202 и текст.
  Некорректный email — 400; общий сбой базы/настроек — 503.
- POST /api/v1/user/reset-password, тело с token, password, confirmPassword.
  Неверная, просроченная или использованная ссылка — одинаковый 400 с invalidToken;
  ошибки пароля/подтверждения — 400 с errors; успех — 200.
- Старый незавершённый endpoint /reset-password/:token заменён запросом с токеном
  в теле: токены не должны попадать в журналы URL.
- Токен — 32 случайных байта. В MongoDB хранятся только SHA-256-хеш и срок,
  скрытые из обычных выборок. Новое письмо заменяет прежний активный токен.
  TTL-индекс пользователей не создаётся: истечение ссылки не удаляет аккаунт.
- В письме токен передаётся во фрагменте #token=..., который не отправляется
  веб-серверу и в HTTP referrer. Страница убирает фрагмент из адреса, сохраняя
  токен только в памяти. После обновления страницы откройте ссылку из письма
  заново. Не добавляйте логирование тел запросов восстановления.
- Одна атомарная операция MongoDB проверяет хеш/срок, меняет хеш пароля,
  удаляет токен и повышает sessionVersion. Одновременные запросы не могут
  использовать ссылку дважды. Старые JWT отзываются на всех устройствах;
  автоматического входа после сброса нет.
- Лимиты на IP: 5 запросов письма и 10 попыток сброса за 15 минут, включая
  ошибочные. 429 содержит Retry-After. Ограничения хранятся в памяти процесса;
  для нескольких серверов нужно общее хранилище, как и для лимитов входа.
- Письмо отправляется асинхронно внутри процесса, без долговечной очереди.
  202 означает принятие запроса, а не подтверждение доставки. При отказе SMTP
  возвращается тот же ответ, хеш неотправленного токена удаляется; в лог попадает
  только общее сообщение без адреса, токена, пароля и ссылки. После исправления
  SMTP запросите письмо заново. Завершение процесса может прервать отправку.

## Языки интерфейса — первый этап

Добавлены i18next/react-i18next и переключатель English / Deutsch / Qırımtatarca /
Русский. При первом посещении выбран английский. Внутренние коды: en, de, qt, ru;
qt всегда остаётся qt в состоянии и localStorage. Выбор сохраняется в отдельном
ключе `kitapstore.language`, синхронизируется между вкладками и не затрагивает
ключи сессии или корзину. Ошибка доступа к localStorage не мешает выбору в памяти.

Заполнены словари en/de/qt/ru, английский остаётся резервным языком.
Все разделы интерфейса переведены; крымскотатарский требует проверки носителем.
Внутренний qt сопоставляется с HTML lang crh-Latn; сам код qt не переименован.
Переключатель больше не показывает уведомление о будущем переводе.
Переключение не меняет URL и не перемонтирует страницы или формы.

### Где находятся тексты

- `frontend/src/i18n/index.js`: единая настройка, языки, HTML lang, хранение выбора.
- `frontend/src/i18n/LanguageSwitcher.jsx`: переключатель языков.
- `frontend/src/i18n/locales/en/*.json`: полные английские словари по разделам:
  common, navigation, footer, auth, catalog, cart, profile, orders, blog, home, messages.
- `frontend/src/i18n/messageAliases.json`: адаптер старых английских сообщений API
  к ключам для совместимости со старыми серверами; новые ответы переводятся
  по code/fieldCodes. Неизвестные сообщения показываются
  как общая ошибка на выбранном языке, а не как технический текст.

Для новой строки добавьте стабильный ключ в словарь нужного раздела и используйте
`t('auth:email')` или `t('catalog:books_count', { count })`. Не используйте перевод
как идентификатор маршрута, поля API, типа книги или статуса в базе. EUR и € —
значения валюты, а не переводимые названия; пересчёта валют нет.

App подписан на изменение языка через useTranslation и обновляет существующее
дерево React без ключей, зависящих от языка. Общая AccountForm дополнительно имеет
свою подписку. Если впоследствии добавляется memo-компонент или отдельный React-root,
он тоже должен подписываться на useTranslation.

Ошибки и уведомления хранятся в состоянии как ключи/параметры либо исходные
сообщения API и переводятся через translateMessage при каждом отображении.
Например, обязательное поле хранится как
`{ key: 'common:required', values: { fieldKey: 'auth:email' } }`.
Это обновляет уже показанную ошибку при смене языка и не очищает введённые значения.
Не сохраняйте результат t() в состоянии для таких сообщений.

Содержимое книг/статей, авторы, язык издания, API и MongoDB не переводились.
Письма восстановления переведены на en/de/qt/ru; прочие уведомления аккаунта пока английские. Даты и числа интерфейса форматируются по выбранному языку; для qt задан
числовой формат ДД.ММ.ГГГГ и 1 234,5. Валюта EUR/€ не меняется.

### Проверка и следующие языки

`npm test --prefix frontend` проверяет полноту ключей/алиасов, отсутствие сырого
пользовательского текста в JSX, английский default/fallback, qt/HTML lang,
хранение выбора, сессии/корзину и перевод существующих ошибок.
Babel parser закреплён как явная тестовая зависимость для проверки JSX.

Чтобы добавить новый язык, создайте словари с теми же логическими ключами,
подключите их в resources, проверьте параметры/множественное число и адаптивность.
Флаг complete означает заполнение всех разделов, а не сертификацию перевода;
крымскотатарскую латиницу нужно проверить с носителем. Не копируйте английские
словари в другие языки, выдавая это за готовые переводы.

Фактически проверены: 9 frontend-тестов, production-сборка, линтер
(0 ошибок, 9 прежних предупреждений useEffect). В браузере: 320/1280 px,
сохранение страницы, ввода и ошибок после смены языка, сохранение языка после
обновления, HTML lang, клиентские и серверные ошибки на изолированной форме
с временными тестовыми переводами. Тестовая форма и тестовые переводы удалены.
Рабочий API/почта/база не использовались. Деплой и push не выполнялись.

Разбиение изменений на локальные коммиты: [I18N_COMMITS.md](I18N_COMMITS.md).

### Переводы de, qt и ru

Текущий этап: [I18N_TRANSLATIONS.md](I18N_TRANSLATIONS.md) — список файлов,
проверки, правила форматирования, спорные формулировки qt и предлагаемое
разбиение на коммиты. На этом этапе коммиты не создавались.

Для чисел в сообщениях используйте `{{count, number}}`, передавая числовой
`count` для выбора формы. Русские семейства требуют one/few/many/other;
крымскотатарские существительные после числительных не получают суффикс
множественного числа. Тест проверяет дополнительные русские формы отдельно
и точное совпадение остальных ключей и параметров. Для новых дат/сумм
используйте formatDate/formatNumber из общей настройки i18n; не форматируйте
значения полей ввода, API или базы данных.

### Язык ошибок API и писем восстановления

JSON-ответы сохраняют прежние message/error/errors, HTTP-статусы и остальные
поля. Дополнительно возвращаются стабильный code и fieldCodes для полей.
Общий контракт: shared/apiCodes.json; подробности и состав коммитов:
[ACCOUNT_LOCALIZATION.md](ACCOUNT_LOCALIZATION.md).

Frontend сначала переводит код, затем поддерживаемое старое сообщение; неизвестная
ошибка получает общий локализованный текст. В состоянии формы хранятся ключи,
поэтому уже показанные ошибки продолжают менять язык.

POST /api/v1/user/forgot-password принимает { email, language }, где language —
строго en/de/qt/ru. Пропущенный, неверный или неизвестный язык означает en.
Frontend подставляет язык в момент отправки. Язык выбирает только тему и текст
письма и не влияет на поиск аккаунта, права, срок токена или публичный ответ.
Новых переменных окружения нет; существующие EMAIL_* и FRONTEND_URL сохраняются.

Проверено: 13 frontend-тестов, 13 backend-тестов с подменённой почтой, сборка
и линтер (0 ошибок, 9 прежних предупреждений). Реальные письма не отправлялись.
