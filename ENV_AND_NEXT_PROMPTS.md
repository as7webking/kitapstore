# Что вводить в .env и как потом публиковать

## Пустые шаблоны

- backend/.env.example — все поля backend с пояснениями и местом ввода.
- frontend/.env.example — единственное поле frontend для выбранной схемы.

Они намеренно пустые: это памятки для заполнения, а не готовая конфигурация.
Твои существующие .env не читались и не изменялись. Файлы .env.example безопасно
хранить в Git только пока там нет настоящих паролей. Не вписывай секреты в example.
Локально секреты вводятся в backend/.env и frontend/.env; они исключены из Git.
В облаке копировать файлы не нужно: вводить переменные в настройках сервисов.
Не перезаписывай рабочий backend/.env тестовым шаблоном.

## Где будут секреты

В текущей схеме Vercel размещает ТОЛЬКО frontend. Его VITE_API_URL публичен.
URI MongoDB, JWT_SECRET, EMAIL_USER/EMAIL_PASS находятся ТОЛЬКО в Environment
отдельного Render backend. Секреты нельзя делать секретными через префикс VITE_:
такие значения становятся частью публичного браузерного JS.

Vercel поддерживает серверные секреты, но этот frontend их не использует.
Просто перенести туда backend/.env недостаточно: backend на Vercel в текущей
конфигурации намеренно не запускается. Если принципиально нужны серверные секреты
и Express именно на Vercel, сначала нужен отдельный этап переноса backend
(общий limiter и корректный жизненный цикл почты), а не загрузка .env целиком.

## Что конкретно вводить в панели

Render → НОВЫЙ тестовый Web Service → Environment → Add Environment Variable:
имя слева из backend/.env.example — в Key, значение — в Value.
Следовать комментариям шаблона. PORT и пустые OAuth-поля в Render не добавлять.
Не использовать рабочие Atlas, SMTP или JWT реквизиты.

Vercel → НОВЫЙ тестовый проект → Settings → Environment Variables:

| Поле | Что вводить |
|---|---|
| Key | VITE_API_URL |
| Value | HTTPS-домен твоего тестового Render API без слеша и /api/v1 |
| Environment | Preview; также Production, если нужен стабильный основной домен отдельного тестового проекта |
| Sensitive | Для API URL не требуется: он публичен в браузере |

В Vercel не добавлять backend-секреты даже как Sensitive: frontend не сможет
использовать их безопасно. Sensitive в панели не скрывает VITE_* из готового JS.
После изменения переменных запускать новую сборку/deployment.

## Что именно отправлять на Vercel — когда решишь публиковать

1. Проверить локальные коммиты. Позже отдельным действием загрузить нужную ветку
   в GitHub; сейчас push и публикация не выполнялись.
2. В Vercel выбрать Add New → Project → импортировать репозиторий kitapstore.
   Создать отдельный тестовый проект; не менять существующее рабочее размещение.
3. Root Directory: frontend. Framework: Vite. Node: 24.x.
4. Включить Include source files outside of the Root Directory in the Build Step,
   потому что frontend импортирует shared/apiCodes.json из корня репозитория.
5. Install Command: npm ci. Build Command: npm run build. Output Directory: dist.
   Эти значения и SPA-переходы уже заданы в frontend/vercel.json.
6. Добавить VITE_API_URL из таблицы. Нужен предварительно настроенный отдельный
   backend. Нажать Deploy только после своего решения публиковать.
7. В Render FRONTEND_URL должен совпадать со стабильным адресом этого frontend.
   Открывать прямые /login, /profile, /forgot-password; проверять API и письма.

Исходники берутся из GitHub, не нужно загружать node_modules, backend/.env или
папку dist вручную. Полная последовательность создания Atlas, Ethereal, Render
и Vercel с учётом их взаимных URL: STAGING_DEPLOYMENT.md. Текущая SMTP-схема
требует Render с исходящим портом 587; бесплатный Render блокирует SMTP.

## Следующие промпты — по очереди

### 1. Проверить заполненную конфигурацию без раскрытия секретов

> Проверь настройки тестового окружения kitapstore. Не выводи значения секретов,
> пароли и URI. Проверь только наличие обязательных переменных, формат адресов,
> отдельную базу kitapstore_test, staging-ограничения и тестовую почту Ethereal.
> Не подключай рабочую базу, не отправляй письма, не делай deployment или push.
> При недоступности облачных настроек подготовь точный список ручных проверок.

### 2. Убрать ограничения памяти процесса

> Замени лимиты регистрации, входа и восстановления kitapstore на общее атомарное
> хранилище MongoDB, сохранив текущие пороги, ответы, коды и Retry-After.
> Проверь одновременные запросы и несколько экземпляров backend, очистку старых
> записей и безопасное поведение при недоступности хранилища. Используй только
> тестовую базу или подмены. Обнови инструкцию. Без deployment и push.

### 3. Сделать доставку писем устойчивой

> Добавь надёжную очередь писем восстановления с отдельным worker, retry и
> ограниченным временем хранения. Сохрани одинаковый ответ для известного и
> неизвестного email, одноразовость токена, отзыв сессий и отсутствие секретов
> в логах. Не рассылай просроченные ссылки и не удаляй более новые токены при
> отказе старой задачи. Тестируй только с подменённой почтой. Без deployment/push.

### 4. Довести магазин до настоящего заказа

> Изучи текущие корзину и заказы kitapstore. Сначала опиши обнаруженные ошибки,
> затем исправь серверную проверку товаров, количества, цен и итогов, создание
> заказа и повторную отправку формы. Цены брать из базы, права проверять сервером.
> Не подключай настоящую оплату, не меняй дизайн и рабочие данные.
> Добавь проверки успешного и ошибочных сценариев. Без deployment/push.

### 5. Ускорить сайт и подготовить файлы

> Оптимизируй изображения logo/hero и загрузку JS kitapstore без изменения
> внешнего вида. Отдельно предложи и реализуй загрузку обложек/PDF в выбранное
> тестовое объектное хранилище с лимитами и проверкой доступа; не мигрируй рабочие
> файлы без отдельного задания. Сравни размеры сборки и проверь ошибки загрузки.
> Если провайдер ещё не выбран, сначала заверши независимую оптимизацию и
> предложи конкретные варианты хранения. Без публикации/push.

### 6. Только после настройки — тестовая публикация

> Опубликуй тестовый kitapstore по STAGING_DEPLOYMENT.md: frontend Vercel,
> отдельный постоянный backend Render, отдельная Atlas kitapstore_test и Ethereal.
> Используй только явно выбранные тестовые проекты. Не трогай рабочие ресурсы,
> не создавай платные услуги без моего отдельного согласия. Не показывай секреты.
> Выполни внешний smoke-test аккаунтов, CORS, SPA и восстановления и сообщи URL,
> фактически выполненные проверки и оставшиеся проблемы.

### Если хочешь принципиально всё приложение на Vercel

> Подготовь перенос Express backend kitapstore в Vercel Functions. Сначала
> проверь актуальную документацию и стоимость нужных возможностей. Сохрани
> существующие API-адреса, подключение MongoDB, приватность восстановления,
> общие лимиты и безопасное завершение фоновой почты. Добавь тесты и инструкцию
> секретных серверных переменных. Не публикуй приложение, не меняй рабочие данные
> и не добавляй секреты в frontend. Объясни оставшиеся ограничения схемы.
