# Проверка перед приглашением тестировщиков

Статус: подготовлены скрипт и сценарий. Внешняя проверка НЕ выполнялась.
Использовать только отдельное тестовое окружение, kitapstore_test, Ethereal и
синтетические аккаунты/книги. Не использовать рабочие аккаунты и заказы.

## 1. Предварительные условия

- Записать проверяемый commit и дату, стабильные frontend/API origins, версию API/worker.
- Подтвердить APP_ENV=staging, изоляцию kitapstore_test и права тестового пользователя.
- Подтвердить Ethereal, общий ключ очереди у API/worker и успешный старт worker.
- FRONTEND_URL совпадает со стабильным HTTPS frontend; VITE_API_URL — с HTTPS API.
- Подтвердить настройки прокси/лимитов перед тестом несколькими людьми.
- Не копировать значения секретов, токены, ссылки восстановления или содержимое
  писем в отчёт, терминал или скриншоты. Сохранять только результаты проверок.

## 2. Автоматический GET smoke — запускать позже вручную

Из корня репозитория:

```sh
npm run smoke:staging --prefix backend -- --staging-api https://YOUR-TEST-API.onrender.com
```

Подставить публичный origin своего тестового API без пути и завершающего слеша.
Флаг --staging-api — явный выбор оператора: скрипт не может доказать по домену,
что сервер действительно тестовый. Настоящие .env не загружаются. Секреты,
авторизация и параметры токенов не нужны; TLS-проверку не отключать.

Скрипт выполняет ровно по одному GET /healthz и GET /api/v1/test, последовательно.
Не вызывает каталог/карточки (просмотр может менять счётчики), регистрацию,
почту, корзину или заказы. Нет POST/PUT/PATCH/DELETE, повторов и redirects.
Каждый запрос вместе с чтением тела ограничен 8 секундами; тело — 4096 байтами.
В логах только PASS/FAIL и фиксированные пути, без ответов и исходных ошибок.

Ожидается:

- /healthz: HTTP 200, JSON content-type и status=ready.
- /api/v1/test: HTTP 200 и текст API OK.
- Код завершения 0 только при успехе обеих проверок; иначе 1.

PASS подтверждает только достижимость этих двух адресов и заявленную readiness.
Он не доказывает правильность прав MongoDB, транзакций, индексов, worker, SMTP,
аккаунтов, восстановления или checkout. HTML-страница с HTTP 200 не проходит.
При FAIL проверить DNS/TLS, доступ к сервису, конфигурацию и логи по безопасным
кодам STARTUP_*. Не обходить ошибки отключением TLS или подменой ответа.

## 3. Ручная проверка — отдельный этап с изменением только тестовых данных

Записывать для каждого пункта PASS / FAIL / NOT RUN и краткое наблюдение.
Ниже операции намеренно создают синтетические аккаунты/заказы и тестовые письма;
они НЕ входят в GET smoke и в текущем этапе не выполнялись.

### Интерфейс и маршруты

- Открыть прямыми ссылками /login, /signup, /all-books, /forgot-password,
  /reset-password и неизвестный URL; обновить страницы. Assets без 404,
  запросов к localhost и ошибок CORS. Неизвестный URL показывает экран 404.
- /profile и /cart без сессии перенаправляют на вход. Проверить возвращение
  после входа на исходную приватную страницу.
- Проверить ширины 360, 390, 768 и 1440: меню, поиск, поля, длинные немецкие
  подписи, названия книг и корзину. Нет горизонтального переполнения.
- Tab/Shift+Tab, Enter, Escape: видимый фокус, закрытые панели не обходятся,
  Escape возвращает фокус на переключатель. Ошибки связаны с полями.

### Аккаунты и сессия

- Зарегистрировать новый синтетический аккаунт. Неверные email/пароль/имя
  показывают локализованные ошибки без сброса остальных введённых значений.
- Повтор того же email, включая регистр и пробелы, не создаёт второй аккаунт.
- Неверный пароль не пускает; правильный вход работает. Обновление страницы
  сохраняет сессию. Обычный аккаунт не получает доступ к admin API/страницам.
- При временном отключении сети ошибка понятна, токен не очищается. После
  восстановления сети повтор проверки сессии возвращает доступ.
- Выход закрывает приватные страницы, включая вторую открытую вкладку.
  Истёкшая/отозванная сессия требует нового входа.

### Восстановление пароля и worker

- Для существующего и неизвестного email одинаковый публичный ответ 202/code/message.
  Реальный неизвестный адрес не использовать: выбрать синтетический.
- Запросить ссылку для тестового аккаунта; письмо появляется только в Ethereal.
  Домен HTTPS совпадает с FRONTEND_URL; токен находится во fragment, не query.
- Новый пароль и подтверждение валидируются; успешный сброс позволяет войти
  новым паролем, старый пароль и старые сессии больше не работают.
- Повторное использование ссылки отклоняется. Новая заявка заменяет предыдущую;
  старая ссылка отклоняется. Отдельно проверить срок действия на тестовом аккаунте.
- На изолированном worker проверить остановку/возобновление: свежая ожидающая
  задача может обработаться, просроченная/заменённая — нет. Проверять только
  метаданные очереди и итог в Ethereal, не открывать payload/tokenHash в отчёте.
- Отказ SMTP и retry проверять только согласованным сбоем тестового транспорта.
  Если не проводился, записать NOT RUN; зелёный healthz не заменяет эту проверку.

### Локализация

- en/de/qt/ru: навигация, формы, ошибки, загрузка, пустые состояния и письма.
- Ввести данные и показать ошибки, затем сменить язык: значения сохраняются,
  ошибки переводятся, сессия и корзина не сбрасываются.
- Выбор языка сохраняется после обновления. Числа/даты форматируются по локали,
  валюта и язык контента книги не меняются. qt отдельно вычитывает носитель.

### Корзина и заказы

- Использовать синтетические книги. Проверить пустую корзину, добавление,
  удаление и корректное отображение цены/доставки.
- Временно отключить сеть: ошибка загрузки не выглядит как пустая корзина.
  После восстановления сети GET-повтор возвращает данные.
- Оформить только синтетический заказ без реальной оплаты. Быстрое повторное
  нажатие не создаёт второй заказ. История показывает сохранённые состав и цены.
- Сервер отклоняет недоступные товары/неверное количество; изменение цены
  в запросе клиента не должно менять серверный итог. Этот пункт проверять
  подготовленным тестовым запросом, без реальных покупательских данных.

## 4. Решение о приглашении

Не приглашать, если FAIL затрагивает вход, приватность, восстановление,
отзыв сессий, повтор заказа, изоляцию базы/почты или HTTPS.
Для непроверенных сценариев явно записать ограничения и определить, можно ли
приглашать только в ограниченный сценарий. Не ставить общий PASS по healthz.
После исправления повторить затронутые сценарии и записать commit результата.

## Проверки этого изменения

Пять тестов используют только подменённый fetch/Response: точные методы и пути,
запрет неверных origins до запроса, статусы/redirect/сеть, проверка тел вместо
одного HTTP 200, лимит размера и timeout запросов/чтения тела. Проверен синтаксис.
Ни внешние smoke-запросы, ни ручные сценарии, ни подключение базы не выполнялись.
